# البنية التقنية — ARUMA MARKET

## الملخص لصاحب المشروع

- **ARUMA MARKET** هي المنظومة (المنصة). **MB Parfum** هو أول «متجر» (store) يعمل داخلها.
- نبني **نظامًا واحدًا منظّمًا في وحدات** (Modular Monolith)، وليس خدمات مصغّرة (Microservices).
  السبب: أسرع في البناء، أرخص في التشغيل، وأسهل في الإصلاح. وكل وحدة معزولة بحيث يمكن فصلها لاحقًا
  كخدمة مستقلة إذا ظهرت حاجة تقنية حقيقية (ضغط كبير على البحث أو الدفع مثلًا).
- قاعدة البيانات مصمّمة من اليوم الأول لتدعم: **عدة متاجر، عدة تجار، عدة دول، عدة عملات، عدة لغات**،
  دون أن نبني الآن شاشات أو منطقًا لا نحتاجه بعد.

## الرؤية وكيف تنعكس على البنية

**الانطلاق:** الجزائر ← إفريقيا ← الأسواق العالمية.

### 1) التطبيقات التجارية (MB …)
MB Parfum، MB Beauty، MB Style، MB Home، MB Tech، MB Sport، MB Drive.

تقنيًا، **كل تطبيق هو صفّ في جدول `stores`** له مجاله (`vertical`)، ولغاته، وعملاته، ودوله، وتصنيفاته، ومنتجاته.
إطلاق MB Beauty مثلًا لا يحتاج كودًا جديدًا في الخادم ولا جداول جديدة، بل:
1. إنشاء المتجر وإعداداته.
2. تحديد خصائص منتجاته (مثلًا نوع البشرة بدل نوتات العطر).
3. واجهة بهوية بصرية خاصة به تعمل على نفس الـAPI.

هذا مُثبَت باختبار آلي (`apps/core/test/multi-store.test.ts`) يشغّل MB Beauty بجانب MB Parfum ويتأكد أن بيانات كل منهما لا تختلط بالآخر.

### 2) خدمات المنصة (ARUMA …)
هذه خدمات مشتركة تخدم كل التطبيقات. كل واحدة ستكون **وحدة (module)** داخل الخادم عندما يحين وقتها،
وتُفصل كخدمة مستقلة فقط إذا ظهر سبب حقيقي (انظر آخر هذا الملف).

| الخدمة | ما تمثّله تقنيًا | ملاحظة للتوسع |
|---|---|---|
| ARUMA Logistics / Delivery | وحدة `shipping` ✅: مناطق التوصيل، الأسعار، شركات النقل (محوّل لكل شركة)، تتبّع الطرود ([SHIPPING.md](SHIPPING.md)) | أول مرشّح للفصل كخدمة مستقلة إذا صار لها أسطول وتطبيق سائقين |
| ARUMA Fulfillment | المستودعات والمخزون حسب الموقع | حاليًا المخزون رقم واحد لكل حجم؛ سيُنقل إلى «مخزون لكل مستودع» عند فتح أول مستودع ثانٍ (تغيير محصور في وحدة واحدة) |
| ARUMA Points | سجلّ نقاط الولاء (دفتر حركات لا يُعدَّل، مثل المال) | نقاط مشتركة بين كل تطبيقات MB |
| ARUMA Ads | ترويج المنتجات للتجار داخل المتجر | يعتمد على بيانات الكتالوج والطلبات |
| ARUMA AI | التوصيات، البحث الذكي، مساعد الزبون | يُبنى فوق الكتالوج؛ قد يُفصل بسبب اختلاف الحوسبة |
| ARUMA Business | حسابات الشركات، أسعار الجملة، الفواتير | يستفيد من جداول الأسعار الحالية |
| ARUMA Developers | API عامة موثّقة، مفاتيح API، Webhooks | لهذا كل مسارات الـAPI تبدأ بـ `/v1` من اليوم الأول |
| ARUMA Support | تذاكر الدعم مرتبطة بالطلبات | — |
| ARUMA Trust & Safety | مراقبة التجار والمنتجات، كشف الاحتيال، التقييمات | يعتمد على `merchants.verification_status` و`store_merchants.status` و`products.status` الموجودَين |

### 3) التوسع الجغرافي
- **الجزائر أولًا:** الدينار الجزائري (DZD) والعربية افتراضيًا، والفرنسية كلغة أساسية ثانية. الدفع عند الاستلام، والتوصيل حسب الولاية.
- **إفريقيا ثم العالم:** إضافة دولة أو عملة أو لغة تتم بإضافة صفوف في جداول `countries` و`currencies` و`locales`
  وربطها بالمتجر، دون تعديل الكود. العملات بدون كسور (مثل الفرنك الإفريقي XOF) أو بثلاث خانات عشرية مدعومة لأن
  عدد الخانات يُحفظ لكل عملة.

## التقنيات المختارة

| الطبقة | التقنية | لماذا |
|---|---|---|
| اللغة | TypeScript (Node.js 22) | لغة واحدة للواجهة والخادم، أخطاء أقل بفضل الأنواع |
| الخادم (API) | Fastify 5 | سريع، خفيف، ناضج |
| التحقق من المدخلات | Zod | كل طلب يُفحص قبل أن يصل للمنطق |
| قاعدة البيانات | PostgreSQL 16 | موثوقة، تدعم المعاملات المالية وJSON والبحث |
| الوصول للبيانات | Drizzle ORM | استعلامات مكتوبة بالأنواع + ملفات migration بصيغة SQL واضحة |
| الاختبارات | Vitest | اختبارات تعمل على قاعدة بيانات حقيقية منفصلة |
| تنظيم الكود | pnpm workspaces (monorepo) | كل التطبيقات والحزم في مستودع واحد |

## هيكل المستودع

```
apps/
  core/                ← ARUMA CORE: الخادم (REST API) المشترك لكل المنصة — انظر CORE.md
    src/modules/       ← وحدة لكل مجال: identity, merchants, stores, catalog, offers, platform
    src/shared/        ← أدوات مشتركة (الأخطاء، المال)
    test/              ← الاختبارات
packages/
  db/                  ← مخطط قاعدة البيانات (ملف لكل مجال في src/schema/)، الـmigrations، والبيانات التجريبية
docs/                  ← التوثيق
```

الواجهات في `apps/` تستعمل نفس الـAPI: `merchant-center` (لوحة التاجر) و`admin` (لوحة إدارة ARUMA، [ADMIN.md](ADMIN.md)). واجهة متجر MB Parfum تأتي لاحقًا.

## نموذج البيانات

```
user (هوية ARUMA واحدة)                 merchant (تاجر)
  ├─ accounts (طرق الدخول)                 ├─ merchant_members (مالك / مدير / موظف)
  ├─ devices                               └─ store_merchants (أين يبيع + العمولة)
  └─ sessions

store (تطبيق: MB Parfum)
  ├─ store_locales    (ar, fr, en)
  ├─ store_currencies (DZD, EUR, USD)
  ├─ store_countries  (DZ)
  ├─ categories ─ category_translations
  ├─ brands
  └─ products ─ product_translations, product_categories, product_images
       └─ product_variants (الحجم، SKU)
            └─ offers (تاجر + مخزون)          ← عدة تجار لنفس المنتج
                 └─ offer_prices (سعر صريح لكل عملة)

platform: audit_logs, domain_events, feature_flags, feature_flag_overrides
```

### قرارات مهمة تمنع مشاكل التوسع لاحقًا

1. **المنتج مرتبط بالمتجر، والبيع يتم عبر عروض التجار.** اليوم MB Parfum هو التاجر الوحيد، وغدًا يبيع عدة تجار نفس العطر دون تغيير الجداول.
2. **المال يُخزَّن كعدد صحيح بالوحدة الصغرى** (سنتيم) مع رمز العملة (ISO 4217). لا نستعمل الأعداد العشرية أبدًا، لتجنّب أخطاء التقريب.
3. **لا تحويل تلقائي للعملات.** لكل عرض سعر محدد لكل عملة. التحويل بسعر الصرف يمكن إضافته لاحقًا كوحدة منفصلة.
4. **النصوص في جداول ترجمة** وليست داخل جدول المنتج. إضافة لغة جديدة = صفوف جديدة فقط. العربية معرّفة كلغة `rtl`.
5. **خصائص كل مجال في حقل `attributes` (JSONB).** للعطور: النوتات، التركيز (EDP/EDT)، الجنس. متجر إلكترونيات مستقبلي يستعمل نفس الجداول بخصائص مختلفة.
6. **المعرّفات UUID** وليست أرقامًا متسلسلة، حتى لا يمكن تخمينها وحتى يسهل دمج البيانات بين الأنظمة.
7. **التواريخ مع المنطقة الزمنية** (`timestamptz`).

## واجهة الـAPI الحالية (v1)

كل المسارات تبدأ بـ `/v1/stores/:storeSlug` ليكون كل طلب مرتبطًا بمتجر معيّن.

| الطريقة | المسار | الوصف |
|---|---|---|
| GET | `/health` | حالة الخادم وقاعدة البيانات |
| GET | `/v1/stores/:storeSlug` | معلومات المتجر، لغاته وعملاته |
| GET | `/v1/stores/:storeSlug/categories?locale=` | التصنيفات مترجمة |
| GET | `/v1/stores/:storeSlug/products?locale=&currency=&category=&page=&pageSize=` | قائمة المنتجات |
| GET | `/v1/stores/:storeSlug/products/:productSlug?locale=&currency=` | تفاصيل منتج مع أحجامه وأسعاره |

- إذا لم تُحدَّد اللغة أو العملة تُستعمل الافتراضية للمتجر (MB Parfum: العربية، الدينار الجزائري).
- إذا نقصت ترجمة لمنتج في لغة ما، يُعرض النص بلغة المتجر الافتراضية.
- الأخطاء بصيغة موحّدة: `{ "error": { "code": "…", "message": "…" } }`.

## متى نفصل خدمة مستقلة (Microservice)؟

فقط عند وجود سبب قابل للقياس، مثل:
- وحدة تحتاج توسعًا مختلفًا جدًا عن الباقي (مثل البحث عند ملايين المنتجات).
- متطلبات أمان أو امتثال تفرض العزل (مثل معالجة بيانات البطاقات).
- فريق مستقل يحتاج نشر وحدته بشكل منفصل.

إلى ذلك الحين، تبقى الوحدات داخل نفس الخادم وتتواصل عبر دوال واضحة، وليس عبر الشبكة.

**أول خدمة منفصلة: الدفع** (`apps/payments`). السبب حقيقي: أسرار مزوّد الدفع وبيانات المال يجب أن تكون معزولة عن باقي النظام. لها قاعدة بياناتها (مخطط `payments`)، وتتواصل مع ARUMA CORE عبر API محمي وأحداث موقّعة. انظر [PAYMENTS.md](PAYMENTS.md).
